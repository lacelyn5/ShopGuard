# ShopGuard — как разбираться в тестировании пошагово

Это инструкции по работе с реальными проверками. Мы специально разделили их по сложности. **Не загружай скриншоты и отчёты на GitHub, пока не проверишь, что там нет токенов, паролей и личных данных.**

## Быстрый запуск интерфейса
1. Распакуй проект в отдельную папку, например `C:\ShopGuard-QA-Automation`.
2. Один раз запусти `scripts\setup_windows.bat` и дождись завершения установки.
3. Запусти `scripts\run_dashboard_windows.bat`. Откроется локальная панель по адресу `http://127.0.0.1:8765`.
4. В панели сначала выбери **Local checks**. Если они прошли, запускай **API checks** и **Browser checks**. Перед онлайн-проверками панель попросит подтверждение.
5. Не закрывай отдельное окно сервера, пока пользуешься панелью. Чтобы остановить её, нажми `Ctrl+C` в окне сервера.
6. Текстовые логи и JUnit XML будут сохранены в `reports\`. Папка исключена из Git.

Панель запускает только заранее заданные наборы тестов и слушает соединения только на этом компьютере. Она не выполняет произвольные команды из браузера.

### Добавить проект и несколько проверок

Раздел **Test projects** хранит до 25 публичных сайтов. Для каждого проекта можно настроить до 20 Browser checks и до 20 API checks.

1. Введи название проекта и публичный **Storefront URL**.
2. В разделе **Browser checks** добавь отдельную проверку для каждой страницы: например `/`, `/products`, `/contact`. Для каждой проверки задай имя, путь и при необходимости ожидаемые фрагменты Page title, видимого H1 и текста страницы.
3. При необходимости добавь **API base URL**. В **API checks** создай отдельную строку для каждого GET endpoint: например `/products`, `/categories` или `/api/health`. Для каждой проверки задай ожидаемый HTTP status, необязательный Content-Type и JSON assertions.
4. JSON assertions записываются по одной на строку:

   ```text
   status = ok
   data.active = true
   meta.total = 3
   data.items[0].id = 42
   data.note = null
   ```

   Используются пути по ключам через точку и индексы массивов с нуля. Целые объекты и массивы сравнивать нельзя. Числа, `true`, `false`, `null` сохраняют тип; обычные слова считаются строками.
5. Нажми **Add project**. Старый формат профиля из предыдущих версий автоматически преобразуется в одну Browser-проверку и, если задан API URL, одну API-проверку.
6. Запустить можно из карточки проекта или в **Test groups → Run checks for a saved project**. Выбери сайт в списке и нажми **Browser**, **API** либо **Run all checks**. Каждая настроенная проверка запускается как отдельный pytest case; общий результат одного запуска попадает в историю выбранного проекта.

Browser checks открывают каждую настроенную страницу во временном Chromium. Они проверяют HTTP-ответ, видимое содержимое, title/H1 и заданные текстовые ожидания. Разрешены только GET/HEAD к тому же хосту. API checks отправляют только GET, не следуют по редиректам и проверяют статус, Content-Type и указанные JSON-поля. Вход в аккаунт, отправка форм, изменение корзины и покупки не выполняются. Тайм-аут запуска увеличивается с количеством настроенных проверок и ограничен 1 000 секундами.

### Подробности ошибок и доказательства

Если одна из проверок падает, ShopGuard сохраняет сообщение из JUnit. Для Browser failure дополнительно пытается сохранить полноразмерный скриншот и JSON-файл с URL, HTTP-статусом, ожидаемыми значениями, фактическим title/H1 и текстом ошибки. Для API failure создаётся JSON-файл с endpoint, ожидаемым и фактическим статусом/Content-Type, полями и причиной ошибки.

Открой карточку проекта → **Run history**. Там доступны **Log**, **JUnit**, **Failure details** и **Screenshot**, если соответствующие файлы созданы. Скриншот и JSON evidence сохраняются в `reports\`; перед отправкой кому-либо проверь их на конфиденциальные данные.

### Analytics

Раздел **Analytics** показывает до 30 последних запусков каждого проекта: количество запусков, процент PASS, число FAIL, среднее время, мини-график длительности и изменение времени относительно предыдущего запуска. Это сводная статистика, а не автоматическое объяснение причины падения или замедления.

### Резервное копирование и восстановление

Открой **Data management**.

- **Create backup** создаёт ZIP в `reports\\backups\\`; в списке можно нажать **Download**, чтобы сохранить его отдельно от папки проекта.
- В ZIP входят профили проектов, история запусков, состояние панели и файлы отчётов, логов, JSON-доказательств и скриншотов, на которые ссылается история. Для вложенных файлов действует общий лимит 15 МБ на копию; если часть старых/крупных файлов не помещается, ShopGuard показывает их количество и записывает его в манифест ZIP. ZIP содержит SHA-256 контрольные суммы. `.env`, `.venv`, пакеты Python и посторонние файлы не включаются. Максимальный размер ZIP — 20 МБ.
- Автоматическая копия создаётся перед добавлением/изменением/удалением проекта и перед восстановлением. Хранятся пять последних автоматических копий. Ручные копии этим лимитом не удаляются.
- Для восстановления выбери ранее созданный ZIP через **Restore backup** и подтверди действие. ShopGuard проверит структуру и контрольные суммы, сначала сохранит текущие данные в автоматическую копию, затем восстановит проекты, историю и вложенные доказательства.

Рекомендую периодически скачивать резервную копию в отдельное место, особенно перед обновлением или удалением папки проекта. Все данные остаются локальными в `reports\` и не попадают на GitHub. Не сохраняй пароли и API-токены в полях проекта и проверяй evidence перед передачей другим людям.

### Проверить другой сайт по ссылке
1. Открой **Check a website**.
2. Вставь публичный адрес, например `https://practicesoftwaretesting.com/`, и подтверди, что у тебя есть право проверять этот сайт.
3. Нажми **Check website** и дождись отчёта.
4. Изучи PASS / WARN / FAIL / INFO. Предполагаемую ошибку обязательно перепроверь вручную.

ShopGuard сначала проверяет HTTP-ответ, затем открывает HTML-страницу в отдельном временном браузере Chromium. Он смотрит заголовок страницы и H1, meta description, наличие атрибута alt у картинок, загрузку изображений, наличие поля поиска, признаки магазина в HTML и отрисованном DOM, ошибки JavaScript и консоли, сетевые сбои и до трёх внутренних ссылок. После первоначальной загрузки сканер дополнительно ждёт до 5 секунд появления видимых карточек товаров, чтобы не пропустить элементы, добавляемые JavaScript с задержкой. Для магазина учитываются `data-test` / `data-testid` / `data-cy` / `data-qa` (в том числе `[data-test="product-name"]`), маркеры карточек и каталога, цены, корзина, кнопки Add to cart, checkout/payment и структурированные Product/Offer-данные. В отчёте показывается количество найденных маркеров. В отчёте также есть категория результата, тип сигнала, серьёзность, уверенность, возможное влияние и следующий шаг.

Важно правильно читать результаты. `FAIL` — более сильный сигнал, например проверенная ссылка с HTTP 404/410; `WARN` — возможная проблема или сетевой сигнал, который нужно перепроверить; `INFO` может означать рекомендацию, непроверенную функцию или ограничение сканера. Пустой `alt` допустим для декоративного изображения, поэтому сканер отличает пустое значение от отсутствующего атрибута. `ERR_BLOCKED_BY_CLIENT` и запросы, остановленные правилами ShopGuard, не выдаются за подтверждённые дефекты сайта.

Это всё ещё быстрая проверка, а не полное тестирование магазина: признаки каталога, цены и корзины являются только DOM/HTML-сигналами со статусом INFO. ShopGuard не нажимает кнопки, не входит в аккаунт, не отправляет формы, не меняет корзину и не оформляет заказы. Если маркеры не обнаружены, это не доказывает отсутствие функций: они могут быть на другой странице, загружаться позже или использовать нестандартные компоненты. Для проверки конкретных сценариев — например, «найти товар и добавить в корзину» — нужны отдельные тесты под выбранный сайт. Если браузер не запускается, ещё раз выполни `scripts\setup_windows.bat` и дождись установки Chromium. Если браузерная проверка недоступна, загрузка изображений будет отмечена как INFO / не проверено, а не как PASS.

## Этап 1. Основы (20–40 минут)
1. Запусти `scripts/setup_windows.bat` только один раз.
2. Запусти `scripts/run_unit_windows.bat`.
3. Прочитай `shopguard/contracts.py`: функция `product_list` проверяет, что API вернул список товаров и служебные поля.
4. Открой `tests/unit/test_contracts.py`, найди проверку неверной цены и пойми, почему она должна падать.
5. Поменяй один тест и повторно запусти набор, затем верни код как было. Цель — увидеть честный `FAIL`.

## Этап 2. API (40–60 минут)
1. Открой в браузере официальный Swagger: https://api.practicesoftwaretesting.com/api/documentation
2. Найди `GET /products`. Посмотри параметры `page` и `sort`.
3. Запусти `scripts/run_api_windows.bat`.
4. Открой `tests/api/test_catalog.py` и объясни, зачем сначала получаем ID товара, а затем отправляем GET `/products/{id}`.
5. Открой Postman, импортируй два JSON из папки `postman/`, выбери environment, запусти коллекцию в исходном порядке.
6. Сравни реальные ответы JSON со встроенными проверками Postman `pm.test`.

## Этап 3. Playwright (45–90 минут)
1. Запусти `scripts/run_ui_windows.bat`. Если браузер не открывается визуально, это нормально: по умолчанию `headless`.
2. Чтобы видеть браузер в Windows CMD: `set HEADED=true`, затем `.venv\Scripts\python.exe -m pytest -m "ui and smoke" -v`.
3. Прочитай `pages/home.py` и `tests/ui/test_storefront.py`: первый описывает действия на сайте, второй формулирует ожидания.
4. Если тест падает, посмотри `reports/*.png` и трассировку: `.venv\Scripts\python.exe -m playwright show-trace reports\имя-файла.zip`.
5. Никогда не меняй `assert` просто для зелёной галочки. Сначала проверь, действительно ли изменилась программа.

## Этап 4. Исследование дефектов (1–2 часа)
1. Запусти `python scripts/compare_environments.py` — это **только сравнение**, не доказательство бага.
2. Выполни ручной сценарий из `docs/TEST_CASES.md` на обычной и buggy-версии Toolshop.
3. Если обнаружил различие, проверь ожидаемое поведение по Swagger/требованиям.
4. Оформи подтверждённую проблему по `docs/DEFECT_REPORT_TEMPLATE.md`.
5. Запиши дату и реальные итоги в `docs/EXECUTION_LOG.md`.

## Что нужно уметь рассказать
- Чем отличается `GET` от `POST`? Почему мы не делаем массовые POST на публичном сервере?
- Что означает `200`, `401`, `404`?
- Чем API-тест отличается от UI-теста?
- Почему тест может упасть из-за сети, а не из-за ошибки продукта?
- Зачем `fixture`, `page object`, `assert`, `pytest marker`?
- Как проверить, что баг воспроизводится, и чем severity отличается от priority?

**Правило:** начинаем с основ и постепенно усложняем проверки. Не нужно заучивать весь проект целиком; важно уметь объяснить и самостоятельно повторить каждое действие.


### Проверка сохранённых сайтов из Test groups

В **Test groups → Run checks for a saved project** выбери сайт в выпадающем списке. Кнопка **Browser** запускает все его Browser checks, **API** — все настроенные GET endpoint checks, а **Run all checks** — оба набора. Если API URL не задан, кнопка API отключена. Новые проекты появляются в списке автоматически; добавленный проект сразу выбирается.

Четыре встроенные группы Local/API/Browser/Full остаются pytest-наборами для демо-магазина Toolshop. Они не подменяются универсальными сайтами: тесты каталога, карточки товара и логина требуют собственных локаторов и сценариев. Для произвольного сайта используй сохранённый профиль и его настраиваемые smoke checks.
